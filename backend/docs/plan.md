# Plan — backend Omnipotent

Ce document est la référence pour développer le backend. Le mettre à jour quand une décision change.

Écrit le 2026-10-25. Les décisions de produit et de modèle sont dans `../../CADRAGE.md` (D1→D48, T1→T5) ; celles du reporting dans `reporting.md` (R1→R14). Ce plan ne les rouvre pas : il dit **dans quel ordre** on les livre.

## Objectif

Une API d'achat média qui conçoit une campagne une fois et la décline, la lance, la pilote et la mesure chez onze plateformes (D50), sur six leviers — Search, DOOH, Audio, Social, CTV & TVS, DAC.

Dans un second temps, le back de multi-search est remplacé par Omnipotent : un levier `search` est créé automatiquement dans chaque campagne, et le front de multi-search s'adapte. Omnipotent ne porte aucun legacy.

## Architecture

```
backend/src/
  modules/<resource>/        HTTP : controller / handler / schema
  mcp/tools/<resource>/      MCP : controller / handler / schema
  services/                  logique métier, partagée par HTTP, MCP et jobs
  types/                     schémas Zod, source de vérité unique
  database/                  entités TypeORM, migrations
  platforms/
    platform-adapter.ts      l'interface commune
    platform-rules.ts        le registre de capacités (ciblage, créas, enchères, quotas, reporting)
    lever-profiles.ts        ce que chaque levier autorise à chaque niveau
    desired-state.ts         l'état voulu, pur
    pacing.ts                le pacing, pur
    <plateforme>/            client + mapping + adapter
  jobs/                      files pg-boss et workers
  ai/                        génération de textes, interface de génération d'images
  plugins/                   auth, organisation courante, base, file de jobs, secrets, S3
```

## Jobs

| Job              | Fréquence                                                | Rôle                                                                                      |
| ---------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `sync.campaign`  | à chaque modification                                    | Applique l'état voulu chez la plateforme                                                  |
| `sync.sweep`     | 1 min                                                    | **Seulement** les unités `pending` ou `error` dont la prochaine tentative est due (D34)   |
| `pacing.refresh` | par campagne, à son minuit local, avec jitter (D34, D47) | Recalcule le budget du jour                                                               |
| `campaign.end`   | 5 min                                                    | Termine par requête les campagnes passé leur date de fin                                  |
| `review.poll`    | 10 min                                                   | Récupère les verdicts de validation                                                       |
| `stats.pull`     | horaire                                                  | Lit les statistiques récentes ; une campagne dont les chiffres bougent est resynchronisée |
| `stats.backfill` | quotidien                                                | Relit une fenêtre longue : les conversions tardives atteignent les rapports               |
| `report.poll`    | 1 min                                                    | Suit les demandes de rapport asynchrones (R14)                                            |
| `account.links`  | 15 min                                                   | Détecte l'acceptation et l'expiration des liens                                           |
| `fx.rates`       | quotidien                                                | Taux BCE                                                                                  |
| `catalog.*`      | selon                                                    | Imports et états des catalogues                                                           |
| `email.*`        | selon                                                    | Envoi, alertes, résumé quotidien                                                          |

## Scalabilité

Voir `../../CADRAGE.md` section 19, « Scalabilité horizontale » (D44→D48). En résumé : API et MCP sans état, workers séparés, montée en charge par réplicas ; un pooler de connexions, un limiteur de débit **partagé entre réplicas** par plateforme, un verrou par campagne, un jitter sur le pacing, un réplica de lecture pour les rapports. **Le plafond réel est le quota des plateformes, pas notre architecture.**

## Comment chaque phase se teste

À la fin de chaque phase, l'application tourne et se teste de trois façons :

- par Swagger (`/documentation`) ;
- par une collection Bruno livrée avec la phase ;
- par MCP depuis Claude Code (fichier `.mcp.json` fourni).

Chaque phase livre les endpoints HTTP, les tools MCP correspondants et **100 % de couverture** de tests. Une phase de plateforme commence par son étude (`../../docs/cadrage-plateforme.md`) et ne se clôt que sur les huit preuves faites sur un compte réel.
